## 目的

Sora Unity SDK Samples を使わず、ドキュメントだけを頼りにアプリを 1 から作ろうとした利用者が困った点を課題として整理し、ドキュメント改善につなげる。SDK をアプリに導入できても、そこからアプリを組み上げるまでの動線が不足している。

## 現状

- ドキュメントは sora-unity-sdk.shiguredo.jp で公開している。README にはドキュメントとサンプルへのリンクはあるが、アプリ開発の手順は書かれていない。
- サンプルは `SoraUnitySdkExamples/` に `SoraSample.cs` と `multi_sendrecv` / `multi_recvonly` / `multi_sendonly` の 3 シーンがある。`SoraSample.cs` は送受信の機能を 1 ファイルにまとめており、機能も多い。
- 実際にアプリを作ろうとした利用者から次の課題が出ている。
  - ドキュメントを開いた時にどこから見ていけばいいか分からない。
  - サンプルは動かせたが、そこから先に進む動線がない。
  - サンプルは機能が多く、使いたい機能をどう組み込むか分からない。
  - SDK をアプリに導入するところまでは分かるが、どう組み上げるか分からない。
  - 「〜をしたい」という目的からどう実装すればよいか分からない。

## 設計方針

- 列挙された課題を、ドキュメントで対応するもの / サンプルで対応するもの / SDK で対応するものに切り分ける。
- 切り分けた結果ごとに対応方針を決め、必要なら個別の issue に分割する。
- ドキュメントは sora-unity-sdk リポジトリとは別に管理しているため、修正先と修正内容を確定させる。

## 完了条件

- 課題が対応先 (ドキュメント / サンプル / SDK) ごとに整理されている。
- それぞれの課題について具体的な対応方針が決まっている。
- 対応が必要なものは個別の issue として起票されている。

## pending にした理由

2026-09-11 に pending にする。

- 課題が利用者の感想として列挙されている段階で、何をどう直すかが具体化していない。ドキュメント・サンプル・SDK のどこで解消するかの切り分けが必要である。
- ドキュメントの修正先が sora-unity-sdk リポジトリとは別であり、担当と修正先を確定させる必要がある。
- 方針が決まるまではドキュメントやサンプルの変更に着手できない。
